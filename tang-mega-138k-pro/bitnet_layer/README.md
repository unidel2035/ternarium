# bitnet_layer — реальный слой BitNet, посчитанный на балансной троичной логике

**Результат (воспроизводимый):** реальный подблок весов модели **BitNet b1.58-2B-4T**
(`blk.0.ffn_down.weight`, 6912×2560, формат i2_s) — 8 нейронов × 16 входов —
посчитан троичным RTL `tritdot.v` (на таблице `trit_mul` и кодировке тритов
из `tritmul.v`/`tritnet.v`: −1=00, 0=01, +1=10) и **побитово совпал с numpy-эталоном**
по всем 8 нейронам.

Это доказывает: главная операция BitNet (Σ wᵢ·xᵢ при wᵢ,xᵢ ∈ {−1,0,+1}) —
это ровно наша балансная троичная логика, без единого умножителя с плавающей точкой.

## Что внутри
- `decode_layer.py` — мини-парсер GGUF (без внешних либ; стоковый `gguf` не знает
  кастомный тип i2_s=36). Достаёт реальные тернарные веса, считает золотой вектор,
  генерит `vectors.vh`.
- `tritdot.v` — троичный dot-product (ядро нейрона BitNet), параметрический по N.
- `tb_tritdot.v` — тестбенч: грузит реальный слой, гоняет M нейронов, сверяет с эталоном.
- `vectors.vh` — авто-сгенерированные веса/вход/эталон из настоящей модели.

## Воспроизвести
```bash
python3 decode_layer.py                       # реальные веса → vectors.vh + numpy-эталон
iverilog -g2012 -o sim tritdot.v tb_tritdot.v
vvp sim                                        # 8/8 нейронов ✓
```

## Ресурсы (yosys, generic synth)
16-входовый троичный MAC = **387 вентилей** (≈150–250 LUT4 на Gowin Arora-V).
На GW5AST-138K (~138 000 LUT) один лейн — ~0.1–0.2% чипа → сотни лейнов параллельно.

## Границы (честно)
- Это **симуляция** (iverilog), не прошивка платы — следующий шаг — bitstream и UART-проверка на железе.
- Считается **целочисленный троичный MAC**; per-tensor scale BitNet — скалярный множитель уже после суммы (на знак не влияет, добавляется тривиально).
- Доказана эквивалентность ядра. Полный слой = много таких лейнов + scale + квантизация активаций.

## Почему это важно
BitNet-веса нативно тернарны. Наш кремний нативно троичен. Их матмул — наш `tritmul`.
Когда выйдут тернарные 14–30B (Microsoft BitDistill в roadmap), троичная ПЛИС
становится естественным ускорителем без FP. Здесь — первый камень: реальный слой
большой модели посчитан балансной троичной логикой и сошёлся с эталоном.

Файлы железной части: `led_witness.v`, `led_witness.cst`, `bake.vh` (вшитые реальные веса), `bake_gen.py`.

### Грабли (зафиксировано для будущих сессий)
- **CST для nextpnr-himbaechel: строго ОДИН `IO_LOC`/`IO_PORT` на строку** (несколько через `;` в строке → «Unconstrained IO» на старшем пине). Формат — как в рабочем `blink.cst`.

1. ✓ Симуляция: реальный слой/нейрон BitNet == numpy (bit-exact).
2. ✓ Bitstream собран и **загружен на реальный GW5AST-138**.
3. ✓ **Результат реального BitNet-слоя виден на светодиодах кремния** (нейрон 0 = 4 статически; цикл 8 значений).

## Прогрессия к троичной LLM (RTL, проверено в симуляции против numpy)

Каждый шаг — на том же `tritdot`/ternary-MAC, веса реальные из BitNet-2B, верификация автономная (iverilog vs numpy, без железа):

| # | Файл | Что | Тест |
|---|---|---|---|
| 1 | `tritreflex.v` | 1 троичный нейрон = голосование большинством (линейно) | 8/8 комбинаций ✓ |
| 2 | `tritmlp.v` | 2-слойная сеть = XOR (нелинейность — один слой не может) | 4/4 ✓ |
| 3 | `tb_ffn.v` (+`ffn_gen.py`) | FFN-блок трансформера: y=W2·ReLU(W1·x), реальные веса blk.0.ffn_* | 8/8 vs numpy ✓ |
| 4 | `tb_attn.v` (+`attn_gen.py`) | Внимание: Q/K/V троичные проекции, QKᵀ, hardmax, ·V, веса blk.0.attn_* | argmax 4/4, выход 32/32 ✓ |

Шаги 3+4 = обе половины трансформер-блока на балансной троичной логике.

### Что ещё нужно для полной троичной LLM (честный остаток)
- **softmax** (вместо hardmax) — fixed-point exp/деление, приближённо (не бит-точно).
- **RMSNorm** перед под-слоями — fixed-point rsqrt.
- **остаточные связи** (residual) — целочисленно, тривиально.
- **эмбеддинг + логиты + сэмплинг** — эмбеддинг это lookup, логиты — тот же троичный матмул.
- **KV-кэш** — BRAM, рост по позиции.
- **стек N блоков + стриминг весов из DDR3** — главная стена (bandwidth DDR3 Tang ограничивает скорость; на кристалл веса не влезают).

Арифметическое ядро обеих половин трансформера доказано. Остаток — нелинейности в fixed-point + память/стриминг (инженерия, не принцип).

## Нелинейности (fixed-point) + память — сделано и проверено в симуляции

Все названные «остатки» закрыты на уровне арифметики (RTL == fixed-point-спека бит-в-бит; спека ≈ float numpy):
| Кусок | Файлы | Тест |
|---|---|---|
| **softmax** (вместо hardmax) | `softmax_gen.py`, `tb_softmax.v` | RTL==спека 32/32; спека≈float (exp-LUT + целочисл. деление, trunc-к-нулю как в Verilog) |
| **RMSNorm** | `rms_gen.py`, `tb_rms.v` | RTL==спека 8/8; ≈float **0.2%** (isqrt с масштабом ²перед корнем для точности) |
| **стриминг весов (память)** | `tb_stream.v` | веса по 1/такт из модели DDR, N=6912 == one-shot (5593) бит-в-бит |

### Уроки (зафиксированы)
- **Floor-деление Python (`//`) ≠ trunc-деление Verilog (`/`)** на отрицательных → спеку считать trunc-к-нулю, иначе off-by-1.
- **isqrt малого числа теряет точность** → масштабировать `ms·SCALE²` ПОД корень, потом делить (0.2% вместо 17%).
- Стриминг весов даёт ту же математику, что параллельный MAC → веса можно держать в DDR, на кристалл не класть.

### Что осталось до полной рабочей LLM на плате (честно — вот это и есть «месяцы»)
Арифметика и нелинейности доказаны по кускам. Остаётся **интеграция**, а не принцип:
- собрать полный блок: RMSNorm→attention(softmax)→residual→RMSNorm→FFN→residual;
- эмбеддинг + логиты + сэмплинг; KV-кэш в BRAM;
- стек N блоков + реальный контроллер DDR3 (double-buffer) + секвенсер;
- синтез всего под GW5AST + bring-up на плате (рабочий канал загрузки).
Каждый шаг — так же sim-проверяем. «30 минут» хватило на ПЛИТКИ (нелинейности+память); полная сборка+синтез+плата — это инженерия на недели-месяцы, но без неизвестных принципов.

## КАПСТОУН: полный троичный трансформер-блок (RTL == fixed-point спека, бит-в-бит)

`block_gen.py` (fixed-point спека+эталон) + `tb_block.v` (RTL мирроринг):
```
h = x + Oproj( Attn( RMSNorm(x) ) )        // внимание + остаточная связь
y = h + FFN( RMSNorm(h) )                  // FFN + остаточная связь
```
- Все 6 матриц весов — **реальные тернарные BitNet** (attn_q/k/v/output, ffn_gate/down).
- Под-слои: RMSNorm (fixed isqrt), attention с **softmax** (exp-LUT), FFN с ReLU, **int8-реквантизация** (shift+clamp) между под-слоями — как в настоящем BitNet.
- **Результат: 32/32 элементов RTL == спека бит-в-бит** (D=8, S=4 токена).

Это закрывает арифметику: не отдельные плитки, а **целый блок трансформера** считается на балансной троичной логике, корректно.

### Полный статус трека «троичная LLM на ПЛИС»
✅ Доказано (симуляция, bit-exact; нейрон — на кремнии):
матмул • FFN • attention • softmax(fixed) • RMSNorm(fixed) • стриминг весов • **полный блок**.
⬜ Остаётся (инженерия, не принцип): стек N блоков • эмбеддинг/логиты/сэмплинг • KV-кэш в BRAM •
контроллер DDR3 с double-buffer • синтез всего под GW5AST + bring-up на плате.

Вывод: **математическое и алгоритмическое ядро троичной LLM доказано полностью**, до уровня целого
трансформер-блока. Дальше — сборка/синтез/плата (недели), без неизвестных принципов.

## TLMM (Table-Lookup Matmul) — приём TeLLMe/T-MAC на нашем tritdot

`tlmm_gen.py` + `tb_tlmm.v`: матмул троичных весов БЕЗ умножений.
- LUT частичных сумм пар активаций (3²=9 на пару) строится **1 раз на токен**.
- Каждый нейрон = только **выборки из LUT + сложения**; веса хранятся компактными **индексами пар** (4 бита/2 веса).
- **Проверено: TLMM == прямой троичный MAC бит-в-бит (8/8)** на реальных весах BitNet.
Выигрыш: умножения в матмуле исчезают; для N нейронов, делящих активации, стоимость амортизируется (LUT строится один раз).

### Бюджет on-chip для Tang (GW5AST-138, ~10 Мбит BRAM)
| Хранение | бит/вес | параметров on-chip |
|---|---|---|
| прямые троичные | 1.58 | ~6.3M |
| TLMM (индексы пар) | 2.0 | ~5M |
| − активации/KV/LUT | — | **реально ~3–5M** |

→ Целиком в BRAM Tang влезает **троичная модель ~3–5M параметров** (например d≈256, ~4 слоя) — без стены памяти.
Энергопрофиль (сообщество): TeLLMe — полная 1.58-бит LLM в 5–7 Вт; TerEffic — 467 ток/с/Вт fully-on-chip.

### Правильная стратегия (по итогам ресёрча)
- ❌ «большая модель в RAM ноута → стрим в Tang» — бьётся о полосу провода (USB2 ~7с/токен на 2B), CPU быстрее.
- ✅ **маленькая троичная модель ЦЕЛИКОМ в BRAM Tang** + TLMM → энергоэффективный on-chip троичный движок (рецепт TerEffic/TeLLMe).
- Ярус: ноут = большой ум; Tang = маленькая троичная модель on-chip как always-on рефлекс/первый проход (то, что CPU не даст по ваттам).
- Больше 5M → внешний DDR3 платы с TLMM (минимум доступов, гибрид TeLLMe), либо суверенный троичный ASIC.

Источники: TerEffic (arXiv 2502.16473), TeLLMe v2 (arXiv 2510.15926).

(Замечание: LUT строится комбинационно — в продакшене его кладут в BRAM последовательно, логика ужмётся.)

## ✅ СИНТЕЗИРУЕМЫЙ СЛОЙ d=256 — реальные цифры P&R (GW5AST-138, верифицировано)

`tlmm_layer.v` — полный троичный линейный слой NIN=NOUT=256 через TLMM, **синтезируемый
и верифицированный**. Веса = 4-битные индексы пар трит в BRAM; LUT частичных сумм
строится 1 раз/токен; compute — выборка+сложение, **ни одного умножителя**.

**Функциональная проверка** (`tb_layer.v`, iverilog): 4/4 нейрона бит-в-бит совпали
с прямым троичным MAC. Формула тактов подтверждена: BUILD `9·CH` + COMP `4·NOUT·CH`.

**P&R (yosys synth_gowin → nextpnr-himbaechel, device `GW5AST-LV138PG484AC0`):**

| Ресурс | Использовано | Всего | % |
|---|---|---|---|
| LUT4 | 5689 | 138240 | **4 %** |
| DFF | 4814 | 138240 | **3 %** |
| BSRAM | 11 (3×DPX9B + 8×SP) | 340 | **3 %** |
| ALU | 190 | 103680 | <1 % |
| MULT/DSP | **0** | 596+298 | **0 %** |
| **Fmax** | **134 МГц** | (P&R timing) | PASS@50 |

Обёртка `pnr_top.v` подаёт слой как on-chip блок (веса/активации в BRAM, наружу clk+led),
чтобы датапас не выпиливался DCE и пины не требовали внешнего интерфейса загрузки.

### Оценка ток/с (multiplier-free, на одном движке)

- Такты/слой d=256: `9·128 + 4·256·128 = 132 224` → при 134 МГц ≈ **0.99 мс/слой**.
- Блок трансформера d=256 ≈ ~10 слой-эквивалентов (Q/K/V/O + gate/up/down) ≈ **~10 мс/блок**.
- Модель ~3.2M парам (d=256, ~5 блоков, помещается в BRAM Tang) ≈ **~20 ток/с** на одном
  наивном движке (4 такта/чанк).

**Запас (инженерия, не принцип):**
1. Конвейеризовать COMP с 4 → 1 такт/чанк (префетч цепочки `wmem→lut` через чанки): **×4** → ~80 ток/с.
2. Один движок = 4 % чипа → ~**25 движков** влезает спатиально (репликация по слоям/блокам).

Итог: для маленькой троичной модели полностью on-chip достижимы **сотни ток/с без единого
умножителя** — согласуется с TerEffic / TeLLMe. Главное доказано: троичный LLM-слой реально
ложится на балансно-троичный кремний Tang.

### Файлы
- `tlmm_layer.v` — синтезируемый слой (BRAM-карта: wmem/lut→block, amem/omem→distributed)
- `pnr_top.v` / `pnr_top.cst` — обёртка для P&R (2 пина, on-chip ROM-веса)
- `tb_layer.v` — функциональный тест против прямого троичного MAC (4/4 OK)

### Уроки P&R под GW5AST
- nextpnr-himbaechel partnumber: **`GW5AST-LV138PG484AC0`** (полный, со speed-grade; `GW5AST-138C`
  и голые `...PG484A`/`FPG676A` дают «No package»). `--vopt family=GW5AST-138C`.
- Память выпиливается DCE, если её выходы не наблюдаются → дать выходной порт + (для distributed)
  реальный порт записи, иначе read-only ROM не ложится на `RAM16SDP4`.
- Большие памяти (wmem/lut) с **одним портом записи** → block (DPX9B/SP); **9 записей/такт**
  (наивный BUILD) не ложатся на BRAM — писать по 1 entry/такт.
- Цепочка из двух зависимых синхронных BRAM-чтений (`wmem→lut`) требует **4 фаз/чанк** в FSM,
  иначе сдвиг на 1 чанк (тихий функциональный баг — ловится только симуляцией).

## ✅ ТРОИЧНЫЙ HDC/VSA-ДВИЖОК — «язык геометрии» на балансной троице (P&R, верифицирован)

`hdc.v` — синтезируемый движок гиперразмерных вычислений над троичными гипервекторами
{−1,0,+1} (код −1=00, 0=01, +1=10, как `tritdot.v` и `pack2bit` в `ternary_comms.py`
передачи данных). Мост софт↔железо: эмбеддер локального эмбеддера даёт троичные вектора,
FPGA исполняет HDC-алгебру **без единого умножителя**.

**Операции** (синтезопригодный чанк-память-стиль: гипервектор хранится словами по
LANES=16 тритов, адресуется индексом — узкие LANES-редукции, чанк/такт):
- `BIND` (Адамар = поэлементный `trit_mul`) — связать ключ⊗значение;
- `BUNDLE` (порог поэлементной суммы → трит) — объединить смыслы в ОДИН вектор;
- `SIM` (троичное скалярное) — близость смыслов;
- `SEARCH` (argmax по item-памяти) — **ассоциативный cleanup**: восстановить смысл из
  сжатого/зашумлённого РЭБ-канала вектора.

**Функциональная проверка** (`hdc_gen.py` numpy-эталон + `tb_hdc.v`, D=384, M=8): **11/11
бит-в-бит**. bundle{0,1,2}→близость к членам {146,153,144}, к чужим ≈0; bind→к частям
{3,−15}≈0 (квази-ортогонально); **cleanup: запрос из item3 с 25% перевёрнутых тритов →
argmax=3** (смысл восстановлен сквозь «глушение»).

**P&R (synth_gowin → nextpnr-himbaechel, `GW5AST-LV138PG484AC0`):**

| Ресурс | Использовано | Всего | % |
|---|---|---|---|
| LUT4 | 5441 | 138240 | **3 %** |
| DFF | 2935 | 138240 | **2 %** |
| ALU | 758 | 103680 | <1 % |
| distributed-RAM (RAM16SDP4) | 344 | 17280 | 1 % |
| MULT/DSP | **0** | 596+298 | **0 %** |
| **Fmax** | **209 МГц** | (P&R timing) | PASS@50 |

(с учётом драйвер-обёртки `hdc_pnr_top.v`; сам движок ещё компактнее).

**Скорость:** NCH=24 чанка. BIND/BUNDLE/SIM = 24 такта; **SEARCH-cleanup = M·NCH = 192
такта ≈ 0.92 мкс @ 209 МГц** → >1 млн ассоциативных распознаваний смысла/с, multiplier-free.

**Интерфейс с бортовой связью** (`ternary_comms.py`): их `pack2bit`/`unpack2bit`
(4 трита/байт, dim0 в младших, 96 байт для D=384) = формат item-памяти движка один-в-один.
Радио-формат base-3 (5 тритов/байт, 77 байт) — для эфира; приёмник распаковывает в 2-бит,
грузит в FPGA, `op=SEARCH` → `out_arg` = распознанный смысл. `jam(frac)` (РЭБ) ложится
прямо в SEARCH-cleanup.

### Файлы
- `hdc.v` — движок (чанк-память: mem/qmem/omem словами W=2·LANES)
- `hdc_gen.py` / `vectors_hdc.vh` — numpy-эталон + init-вектора (D=384)
- `tb_hdc.v` — функциональный тест против numpy (11/11)
- `hdc_pnr_top.v` — обёртка для P&R (clk+led, LFSR-драйвер, op по счётчику)

### Уроки синтеза HDC
- Широкие **переменные part-select** в плоский 2·D-битный регистр (`out_hv[2*idx+:2]`)
  вешают yosys (PROC_MUX/ABC9 не сходятся за минуты). Решение — **чанк-адресуемая память**
  словами фиксированной ширины (как BRAM в `tlmm_layer`): `mem[s*NCH+c]`, под-индекс `[2*j+:2]`
  с константным j.
- Генератор паттерна `t*const` в обёртке инферит `MULT18X18` → нехватка BEL. Для заполнения
  памяти на P&R — **LFSR/XOR-shift**, без умножения.
- Константные управляющие входы движка в обёртке → opt сворачивает FSM в константу и
  выпиливает датапас. Гнать `op` по счётчику (все ветви достижимы) + непрерывно писать/читать
  память → ничего не выпиливается.

## ✅ БОРТОВОЙ ПРИЁМНИК «языка геометрии» — radio → смысл на железе (P&R, верифицирован)

`rx_hdc.v` — единый RTL-блок приёма: радио-пакет (base-3, 5 тритов/байт, формат `pack()`
из бортового `ternary_comms.py`) → аппаратная распаковка ROM-таблицей (3⁵=243≤256, **без
делений**) → посборочный конвейер чанков запроса → `SEARCH` по словарю смыслов в item-памяти
→ распознанный индекс. От РЧ-байтов до смысла — целиком на троичном кремнии, multiplier-free.

**Сквозная проверка** (`tb_rx.v`): словарь из 8 смыслов загружен, в эфир подан реальный
77-байтный пакет зашумлённого (РЭБ, 25% перевёрнутых тритов) запроса item3 → приёмник
распаковал, собрал, выполнил cleanup → **recog = #3** (совпало с numpy-эталоном). Радио-формат
`pack()`/`unpack()` передачи данных воспроизведён в железе бит-в-бит.

**P&R (`GW5AST-LV138PG484AC0`, LANES=8):**

| Ресурс | Использовано | Всего | % |
|---|---|---|---|
| LUT4 | ~1630 | 138240 | **1 %** |
| ALU | 184 | 103680 | <1 % |
| DFF | 1061 | 138240 | <1 % |
| distributed-RAM | 108 | 17280 | <1 % |
| MULT/DSP | **0** | — | **0 %** |
| Fmax | **≈50 МГц** (49–58 по размещению) | — | — |

Приёмник делает только `SEARCH`, поэтому ветви BIND/BUNDLE и память результата выпилены —
он компактнее полного движка. LANES=8 (а не 16) укорачивает редукцию `cdot`/такт → проходит
тайминг. SEARCH = M·NCH = 8·48 = 384 такта ≈ **7 мкс/распознавание** @ 50 МГц — на порядки
выше реального темпа РЧ-пакетов.

### Файлы
- `rx_hdc.v` — приёмник (unpack3 ROM + ассемблер чанков + движок hdc, op=SEARCH)
- `unpack3_rom.vh` — ROM base-3→5 тритов (генерится `hdc_gen.py`)
- `vectors_rx.vh` / `rx_pkt_load.vh` — тестовый радио-пакет (77 байт) + ожидаемый индекс
- `tb_rx.v` — сквозной тест radio→recog (LANES=8)
- `rx_pnr_top.v` — обёртка для P&R (clk+led)
